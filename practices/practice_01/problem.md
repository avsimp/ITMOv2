# Проблема и метрики

## Проблема

В выбранном учебном сценарии инженер отправляет diff в API и использует результат при ручном ревью. Вместо помощи он может получить необработанную ошибку при отсутствующем поле `diff`, неопределённое ожидание или ответ без проверяемых аргументов. Инженеру приходится выяснять причину и повторять запрос, а качество ревью нельзя оценить только по числу замечаний.

Подтверждено фрагментом: обращение по отсутствующему ключу (`TRAINING_PR.diff:37`), вызов LLM без локального перехвата исключений (`:21`), отсутствие требований к содержанию ответа в промпте (`:20`). Наличие глобальных обработчиков и таймаутов неизвестно. Число реальных ошибок и потраченное пользователями время не измерены.

MVP: валидация и ограничение входа, предсказуемые ответы об ошибках LLM, проверяемая структура комментария и минимальные метрики. Решение о merge остаётся у человека. Реализация кода и промышленный rollout не входят в сдачу Practice 1.

## Метрики

Все цели ниже — предложенные критерии MVP из [Context Pack](context.md#context-pack). Baseline по реальному сервису отсутствует; значения не выдумываются. Знаменатель 0 означает «нет данных», а не 0% ошибок или 100% успеха.

| ID и показатель | Формула / метод | Baseline | Цель | Источник и окно |
|---|---|---|---|---|
| M1. Некорректный вход обработан предсказуемо | Число запросов с известным невалидным входом и ожидаемой парой status/code / все запросы набора невалидного входа × 100% | Не измерен; `{}` вызывает KeyError в показанном коде | 100%; 0 вызовов LLM для этого набора | Отчёт I1–I3, E2–E3 и spy адаптера; каждый запуск приёмки |
| M2. Ошибки провайдера контролируются | Число инъекций сбоя, получивших ожидаемую пару status/code / все инъекции сбоя × 100% | Не измерен; в показанном методе нет try/except | 100%, без HTTP 500 и необработанных исключений в тестируемых сценариях | I5–I7, E4; каждый запуск приёмки |
| M3. Инженер получает пригодное ревью | Ответы на фиксированный учебный набор diff, удовлетворяющие всем R7 / все ответы этого набора × 100% | Исторические ответы разобраны в prompts.md; сопоставимого количественного baseline нет | 100% на двух учебных примерах перед приёмкой; это не оценка качества на всех PR | Ручная проверка файла/условия/доказательства и максимум 3 рисков; E5 |
| M4. Задержка при штатной нагрузке | p95 времени от отправки HTTP-запроса до полного ответа; отдельно число завершённых / отправленных запросов | Не измерена | p95 ≤ 500 мс на стенде со stub LLM 100 мс; завершены все запросы | L1: после 30 с прогрева, окно 5 мин; это цель стенда, не SLO реальной LLM |
| M5. Неожиданные серверные ошибки | События review_completed со status=500 / все review_completed × 100% | Не измерена | 0% на приёмке; после реализации любое status=500 требует расследования | R6-логи; тестовый прогон, затем суточное окно учебного стенда |

Контролируемые 502/504 учитываются отдельно: их сокрытие переводом в 200 не считается улучшением. Тестовый отчёт содержит число отправленных запросов и итоговых событий; отсутствующий event является ошибкой наблюдаемости, а не поводом исключить запрос из статистики.

## Почему метрики подтверждают решение

M1 показывает, что пользователь может исправить ввод и не расходует вызов LLM на заведомо невалидные данные. M2 проверяет предсказуемое завершение отказов, а M4 — накладные расходы сервиса. M3 связывает технический API с полезностью для ревьюера: замечание должно быть проверяемым, а не просто длинным. M5 помогает обнаруживать оставшиеся дефекты обработки запросов. Эти метрики не доказывают снижение времени ревью без отдельного замера работы людей.
