# Use cases и user stories

## Первый рабочий сценарий

Инженер отправляет учебный diff в API, получает комментарий с проверяемыми замечаниями или понятную ошибку. Он самостоятельно проверяет выводы и решает, что исправлять в PR. Целевой контракт — [R1–R7](context.md#context-pack); численные пороги предложены для MVP, а не извлечены из diff.

## Use cases

| ID | Актор / триггер | Предусловия | Основной ход и результат | Альтернативы |
|---|---|---|---|---|
| UC1 | Инженер отправляет POST /api/reviews | Учебный стенд доступен; у инженера подготовлен синтетический diff | Проверка входа → один вызов LLM → 200/comment → инженер проверяет доказательства | Невалидный ввод → 422 или 413 без вызова LLM; сбой → 502; дедлайн → 504 |
| UC2 | Инженер сопровождения разбирает неуспешный запрос | Доступ к техническим событиям стенда | По request_id находит один итоговый event, статус, длительность и факт вызова LLM | Событие отсутствует/дублируется — дефект наблюдаемости; исходный diff в логах не нужен |

## User stories и acceptance criteria

- **US1.** Как инженер, я хочу получить понятную ошибку при неправильном diff, чтобы исправить запрос без бесполезного вызова модели. AC: R1, R2, R5; проверки I1–I3, E2–E3.
- **US2.** Как ревьюер, я хочу получить доказательный комментарий либо явное сообщение об отказе за ограниченное время, чтобы решить, продолжать ли ревью или повторить запрос позже. AC: R3–R5, R7; I4–I7, E1, E4–E5. Повтор решает человек, автоматического retry нет.
- **US3.** Как инженер сопровождения, я хочу видеть исход и длительность запроса без содержимого кода в логах, чтобы расследовать сбой и считать метрики. AC: R6; I8, L1–L3.

```gherkin
Feature: Предсказуемый помощник ревьюера PR

  Scenario: Позитивный запрос
    Given LLM возвращает непустую строку "Проверено"
    When отправлен POST /api/reviews с JSON {"diff": "diff --git a/a.py b/a.py"}
    Then статус равен 200 и тело равно {"comment": "Проверено"}
    And LLM вызвана ровно один раз

  Scenario Outline: Невалидный ввод
    When отправлен POST /api/reviews с JSON <body>
    Then статус равен 422 и error.code равен "invalid_diff"
    And error.message непустой и LLM не вызвана
    Examples:
      | body              |
      | {}                |
      | {"diff": 123}     |
      | {"diff": null}    |
      | {"diff": ""}      |
      | {"diff": "   "}   |
      | []                |

  Scenario: Граница длины
    Given LLM возвращает "Проверено"
    When diff содержит ровно 10000 символов "x"
    Then статус равен 200 и LLM вызвана один раз
    When отдельный запрос содержит diff из 10001 символа "x"
    Then статус равен 413 и error.code равен "diff_too_large"
    And для этого запроса LLM не вызвана

  Scenario: Истечение дедлайна
    Given адаптер LLM не завершает вызов до дедлайна 5 секунд
    When отправлен валидный diff
    Then статус равен 504 и error.code равен "llm_timeout"
    And запрос завершён не позднее 5.5 секунды на ненагруженном тестовом стенде
    And автоматического повтора нет

  Scenario: Ошибка провайдера
    Given адаптер LLM сообщает о сетевом сбое
    When отправлен валидный diff
    Then статус равен 502 и error.code равен "llm_failure"
    And traceback и содержимое diff отсутствуют в ответе

  Scenario: Наблюдаемость
    When завершён запрос с невалидным diff
    Then записан ровно один event "review_completed"
    And status равен 422 и llm_called равен false
    And в событии нет diff, промпта и ответа LLM
```

200 с заглушкой «Проверено» проверяет транспортный контракт, а не качество ревью. Содержательность ответа реальной модели проверяется отдельно в E5 по R7; формальное прохождение HTTP-теста не заменяет эту проверку.

## Как использовали AI

- Сессия: [P1-04](prompts.md#журнал), OpenCode / anthropic/claude-sonnet-5.
- Тип: master prompt.
- Задача: добавление user story и разделение сценариев.
- Оценка результата: В ответе добавлена явная user story. Проверка неверного типа является негативным случаем; границу размера нужно проверять отдельно.
