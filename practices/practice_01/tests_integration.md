# Integration-проверки

Статус: **план после реализации**, результаты пока отсутствуют. Проверяется граница HTTP → валидация → сервис → адаптер. Контракт: [R1–R7](context.md#context-pack).

Стенд: FastAPI-приложение с fake LLM, считающим вызовы, и сборщиком событий. В исходном diff `review_service` импортирован как объект, а не через `Depends`: подмена должна выполняться в месте использования `app.api.review_service`. После введения фабрики приложения способ подмены фиксируется в тестовой конфигурации. Для проверки настоящего HTTP 500 при регрессии клиент должен возвращать серверные ответы, а не пробрасывать исключения в тестовый процесс.

| ID / правила | Вход и настройка | Ожидаемый результат |
|---|---|---|
| I1 / R1, R5 | POST с каждым входом U1; отдельно тело `{` с Content-Type application/json | HTTP 422, error.code=invalid_diff, непустой message, нет traceback/исходного тела; 0 вызовов LLM |
| I2 / R1, R3 | POST `{"diff":"x","extra":"ignored"}`; fake отвечает `"ok"` | HTTP 200, ровно `{"comment":"ok"}`; extra не попадает в промпт; 1 вызов |
| I3 / R2, R5 | POST со строками U2 длины 10000 и 10001, включая Unicode; fake отвечает `"ok"` | 10000 → 200 и 1 вызов; 10001 → 413/diff_too_large и 0 вызовов. Отдельно воспроизводит риск большого входа из ADR |
| I4 / R3 | Валидный diff, fake отвечает `"Проверено"` | 200, ровно `{"comment":"Проверено"}`, Content-Type application/json; 1 вызов |
| I5 / R4, R5 | Валидный diff; транспорт возвращает сетевую ошибку | 502/llm_failure, непустой message без внутренних деталей; 1 попытка, без retry |
| I6 / R4 | Локальный stub провайдера держит соединение 10 с; включён реальный адаптер с общим дедлайном 5 с | 504/llm_timeout не позднее 5.5 с на ненагруженном стенде. Операция клиента отменена, число активных операций адаптера вернулось к исходному; повторов нет. Отмена не доказывает прекращение вычислений удалённого провайдера |
| I7 / R4 | Fake по очереди возвращает null, число, пустую и пробельную строки | 502/invalid_llm_response, не 200 и не необработанный 500; 1 вызов на запрос |
| I8 / R6 | Выполнить по одному запросу из I1, I3 (10001), I4, I5, I6, I7 с различимыми request_id | Ровно один review_completed на запрос. Поля R6 заполнены, duration_ms ≥ 0, llm_called=false для отклонённого ввода и true для остальных. Контрольная строка из diff и ответа отсутствует во всех логах |

Проверка R5 общая для I1/I3/I5–I7: точное совпадение status и error.code; message — непустая строка, проверяется смысл, а не дословная формулировка. Для I8 дополнительно проверяется полнота: число итоговых событий совпало с числом отправленных запросов.

Артефакт будущего прогона: таблица ID → запрос → ответ → число вызовов → событие → pass/fail. Для I6 дополнительно длительность и число активных операций до/после. Приложение и продуктовые тесты ещё не реализованы; `make test` не выполняет эту таблицу.

## Как использовали AI

- Сессия: [P1-03](prompts.md#журнал), OpenCode / anthropic/claude-sonnet-5.
- Тип: master prompt.
- Задача: подготовка проверок API, сервиса и LLM.
- Оценка результата: Рассмотрены отсутствие поля, неверный тип и ошибка LLM. Формулировку «контролируемый ответ» необходимо раскрывать через конкретный статус и результат.
