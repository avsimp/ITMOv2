# Data Model: HTTP-слой подборщика

**Статус**: согласованная модель для контракта `1.0.0`, 2026-10-27;
реализация ещё не выполнена.
Нормативные публичные поля и примеры — в
[общем api-v1.yaml](../../../contracts/api-v1.yaml); этот документ описывает связи,
валидацию и внутреннее хранение, не является второй схемой API.

## Категория и страница поиска

Категория имеет ID источника и title, принадлежит каноническому номеру ЕГЭ.
Номера 20/21 нормализуются в 19; исходное значение запроса сохраняется отдельно.
Набор категорий запрашивается у Bank, не фиксируется в приложении.

Страница поиска связывает фильтры с total, offset, limit, next_offset и Task.
Все фильтры применяются до разбиения; порядок Bank не меняется.
Пустая страница с ненулевым total возможна при offset >= total.
Предыдущее смещение хранит UI; снимок внешнего банка между страницами не гарантируется.

## Task и исходная задача

Публичный Task — проекция для выбора: ID, ege_numbers, условие, происхождение,
адреса изображений/приложений. ID — номер генератора, не позиция в работе.
Тройка всегда `[19,20,21]`, один объект/пункт/ID.

`statement_html` публичного Task содержит безопасный фрагмент с адресами API;
images/attachments согласованы с его src/href. Не содержит answer/answer_html.
Проекция не мутирует исходную задачу Bank.

OriginalTask в преподавательском SourcesManifest — исходный нормализованный объект Bank,
включая оригинальные адреса, answer/answer_html. Он сохраняется экспортёром в момент
создания и не заменяется публичной проекцией. Экспорт получает ID и заново загружает оригинал.

## TaskResource

Ресурс определяется тройкой topic_id, kind, source URL. Kind разделяет image/attachment.
При каждом GET проверяется точное вхождение URL в соответствующий список Bank.get.
URL не является локальным путём. Его каноническая проверка и fetch сохраняют ограничения
домена/redirect банка. Ресурсная выдача — живое представление, не неизменяемый снимок.
Изменение источника может сделать прежний URL недоступным, но не заменяет его другим ресурсом.

## Запрос создания и Work

Запрос содержит обязательные уникальные topic_ids в нужном порядке и необязательное name.
Число ID 1–100, каждый — положительный int без bool/строк/дробей.
Порядок не сортируется и не дедуплицируется молча: повтор — ошибка.
Неизвестные поля, в том числе output_path и текст условий, запрещены.

Явное name проверяется после strip: 1–80 символов, без управляющих символов,
разделителей путей, `.`/`..` и префикса диска. Null/пустое имя не означает отсутствие.
Автоматическое имя формируется в UTC и возвращается UI. Ни одно имя не задаёт путь.

Work идентифицируется UUIDv4, а не именем или хешем состава. Разные создания,
включая одинаковые ID/name, имеют разные ID и каталоги. Count равен длине topic_ids;
материалы относятся к зафиксированному порядку, не текущей подборке UI.
Идемпотентность между POST и восстановление по имени/составу отсутствуют.

## Artifact и преподавательский manifest

Результат связывает работу с дескрипторами result/pdf/archive/answers/sources
по схеме общего контракта. Каждый имеет URL API, безопасное имя, MIME и audience.
Ответы/источники как содержимое в Work отсутствуют.

Без приложений result — PDF, archive — null. При приложениях result — ZIP,
archive описывает те же байты, pdf — отдельный просмотр. В ZIP только work.pdf
и work.files с приложениями. Answers и sources существуют вне ученического архива.

Manifest экспортёра содержит format_version=1, время, оригинальные tasks,
SHA-256 PDF, имена приложений и attachment_map. Карта привязывает позицию пункта,
ID, исходный URL/имя и новый относительный путь. Единственное приложение — N.ext,
несколько — N_1.ext и далее в порядке первого появления URL. Расширения сохраняются.
Исходные байты скачиваемых материалов и JSON не меняются при GET.

## Внутренний файл work.json

Расположение: `api/var/works/<uuid>/`. Каталог создаётся эксклюзивно, основа фиксирована:

```text
<uuid>/
├── work.pdf
├── work.answers.txt
├── work.sources.json
├── work.files/          # только если есть приложения
├── work.zip             # только если есть приложения
└── work.json            # завершающий маркер готовности, не скачивается отдельным kind
```

Внутренние метаданные: schema_version=1, work_id, name, created_at, topic_ids,
count, attachments, фиксированные относительные имена артефактов и признак архива.
Публичные URL строятся из настроенного origin и ID, не сохраняются как пути диска.
На перезапуске данные читаются по известному ID без глобальной таблицы или сканирования
истории. Повреждённый JSON — internal_error, отсутствующий/незавершённый — not_found.

Файл маркера публикуется атомарно после закрытия всех артефактов и проверки ожидаемого
состава/путей: временный файл в том же каталоге → flush/fsync → rename.
Существующий маркер или выходные файлы не перезаписываются; каталог новый и принадлежит
только этой попытке. Проверяется отсутствие symlink и выходов за каталог работы.
Сохранность после штатного перезапуска обязательна; транзакция при аппаратном отказе
питания не обещается.

## Переходы состояния

1. **Validated**: запрос допустим; это внутренний шаг, не ответ клиенту.
2. **Creating**: UUID/каталог выделены, export_pdf выполняется в рабочем потоке.
   Публичного job/status нет; GET до маркера возвращает 404.
3. **Ready**: все материалы готовы, валидный work.json опубликован, разрешён 201/GET.
4. **Failed before ready**: возвращается ошибка; маркера нет, частичные файлы непубличны.
   Удаление незавершённого каталога — ручная операция.
5. **Partially cleaned / Removed**: удалён материал либо каталог/маркер.
   Известный отсутствующий файл — 404; оставшиеся файлы с маркером доступны.
   Автоматического восстановления или экспорта по GET нет.

**Unknown outcome** — только состояние UI после потери подтверждения; сервер в это время
может быть Creating, Ready или Failed. Оно не сохраняется в Work как статус отказа.
Disconnect не удаляет каталог. Повторный POST начинает отдельную работу и может дать дубль.

## Ошибки и пути

Код/сообщение/fields соответствуют общей ErrorResponse. Fields указывает имя входного поля,
не содержит сырого значения пути. Файловые дескрипторы — фиксированное серверное
соответствие kind → относительное имя; клиентские name, filename или source URL
не участвуют в локальном path join. Отсутствие отдельного файла не делает все Work
нечитаемым: метаданные не пересобираются как проверка целостности всей работы при каждом GET.
