# Quickstart и будущая приёмка HTTP-слоя

**Дата**: 2026-10-27. **Статус**: руководство будущей проверки согласованного API `1.0.0`.
API и его проверки реализованы. Приведённые ниже сценарии остаются руководством
приёмки; фактически выполненные прогоны отдельно записаны в
[api-verification.md](../../../evidence/api-verification.md).
LIVE-UI пока заблокирован отсутствием настоящих index/assets; тестовая статика
не считается готовым компонентом UI. Исходные снимки требований не переписываются.
Основные ссылки: [контракт](../../../contracts/api-v1.yaml),
[модель](data-model.md), [план](plan.md), [соглашения](../../../evidence/agreements.md).

## 1. Проверить согласованный контракт сейчас

Из `practices/practice_05/homework/api/`, при установленном uv:

```bash
uvx --from openapi-spec-validator openapi-spec-validator ../contracts/api-v1.yaml
```

Ожидается успешная структурная проверка OpenAPI 3.1, внутренних ссылок и допустимости
схем. Это не проверка выполнения сценариев HTTP. Подтверждение UI и принятие
пользователем записаны в соглашениях; текущая версия контракта — `1.0.0`, статус `agreed`.
При изменении примеров дополнительно проверять соответствие JSON-примеров их схемам.
Не копировать общий YAML в api/specs или UI.

## 2. Подготовить окружение и запустить API

Предварительные условия: контракт согласован; Python 3.11+, доступный исходный проект
ДЗ 3, зависимости FastAPI/Uvicorn и исходного экспортёра, установленный Chromium,
файлы UI `index.html` и `assets/` нужны для настоящего браузерного прогона.
Без них API доступен, а статика возвращает 404. Закреплённые зависимости API/ДЗ 3
содержатся в requirements-api.txt, проверок — requirements-dev.txt; исходные модули не скопированы.
Выбранный baseline файлового транспорта — FastAPI 0.162.0 и Starlette 1.10.0.
При изменении Starlette повторно сверить Range-исключения с общим контрактом.

Из корня API, при установленном uv:

```bash
uv venv .venv
uv pip sync --python .venv/bin/python requirements-dev.txt
.venv/bin/python -m playwright install chromium
.venv/bin/python -m uvicorn app.main:app --host 127.0.0.1 --port 8000 --workers 1
```

Открыть `http://127.0.0.1:8000/`. UI и `/api/v1` обслуживает один процесс;
отдельный frontend dev server, CORS proxy, БД и очередь не нужны.
Не использовать `--reload` во время проверки длительного создания.
Экспорты сохраняются в `api/var/works/`; до ручной очистки не удалять этот каталог
между перезапусками. Настройка origin должна совпадать с портом запуска.

## 3. Категории, поиск и отображение

```bash
curl -i "http://127.0.0.1:8000/api/v1/categories?ege_number=20"
curl -i "http://127.0.0.1:8000/api/v1/tasks?ege_number=5&limit=1&offset=0"
curl -i "http://127.0.0.1:8000/api/v1/tasks?ege_number=5&limit=31"
```

Ожидается соответственно: 200 с каноническим 19; страница без answer/answer_html;
422 общего формата. Перейти по next_offset с теми же фильтрами до null; пустой результат
или offset >= total — 200 с tasks=[]. Предыдущие смещения хранит UI.

В карточке с рисунком/таблицей/приложением проверить сохранение содержимого и атрибутов,
API-URL в HTML и массивах ресурсов, отсутствие кода источника и локальных путей.
Открыть выданный URL изображения: 200 с разрешённым MIME; приложение скачивается
как octet-stream, не открывается как HTML UI. Подмена URL на чужой ресурс задачи — 404;
недоступность источника — 502/504. Ошибка картинки видна в карточке и не считается
нормальной пустой выдачей или гарантией пригодности экспорта.

Числа и наборы ID живого сайта могут измениться. Фиксированные примеры из контракта —
иллюстрации формата; перед живой проверкой выбрать доступные реальные задачи.

## 4. Создание PDF без приложений

Сначала подтвердить, что выбранные ID доступны и не имеют приложений. Исторический
набор `[9048,9080,9175]` — ориентир из ДЗ 3, не обещание текущего состояния сайта.

```bash
curl -i -X POST "http://127.0.0.1:8000/api/v1/works" \
  -H "Content-Type: application/json" \
  --data '{"topic_ids":[9048,9080,9175]}'
```

Ожидается один 201 после полной готовности: имя назначено сервером, новый UUID,
count=3, result PDF, archive=null, отдельные pdf/answers/sources. Полученные URL
использовать напрямую; при скачивании через curl сохранять результат в заранее
выбранный клиентский каталог, не передавать этот путь серверу.

Скачать result дважды, сравнить байты; скачать ответы и sources отдельно.
Проверить нумерацию, оригинальные рисунки и условия, отсутствие ответов/источников
в PDF, три вопроса игры как один пункт. Для доказательства пригодности выполнить
и автоматическую проверку PDF, и визуальный просмотр.

## 5. Создание ZIP и перенос

Создать работу с игрой и подтверждённой задачей с приложением; исторический пример
`[9175,9111]`. Результат 201: result ZIP, archive не null, pdf для просмотра отдельно.
Скачать result, полностью распаковать в другой каталог, не рядом с серверными файлами.

Проверить: в ZIP только work.pdf и work.files; одиночное приложение второго пункта —
2.ods при соответствующем исходном расширении. Все относительные ссылки разрешаются
к существующим файлам с исходными байтами; answers/sources снаружи архива.
PDF для просмотра совпадает с PDF внутри ZIP; result и archive дают одинаковые байты.
Открытие приложения по клику конкретного PDF-просмотрщика проверять отдельно и не
подменять проверкой одной лишь существующей цели ссылки.

## 6. Ошибки и повторные запросы

- POST с пустым списком, 101 ID, повторами, отрицательным ID, bool/дробью/строкой,
  name=null, пустым именем, output_path или чужим полем — 422 без публикации работы.
- Неверный JSON — 400; POST с другим Content-Type — 415; неподдержанный метод — 405.
  Это прикладные JSON ErrorResponse, не текстовые Range-ответы файлового транспорта.
- На контролируемом экспортёре проверить POST точного `/api/v1/works`:
  прямой ответ без redirect-цепочки, ровно один вызов экспортёра. Затем POST
  `/api/v1/works/` при отключённом следовании redirect: JSON 404 `not_found`,
  нет Location, 307/308 и вызова экспортёра. Повторить с клиентом, разрешающим redirect:
  результат всё равно 404, новых вызовов нет. Это проверяет настройку сервера,
  а не только осторожность UI. В контролируемом UI-сценарии навязанный 307/308
  не должен переотправить POST: Fetch использует `redirect: "error"`, исход неизвестен,
  автоматического повтора нет.
- Недопустимая категория — 422, отказ/redirect/изменённая разметка источника — 502,
  распознанный сетевой timeout — 504. Неполная игра не выдаётся как полная задача.
- Контролируемый конфликт выходного файла/символической ссылки — 409;
  отказ рендеринга/записи — 500. Существующие байты не изменяются,
  каталог без завершающего work.json не доступен для скачивания.
- Два явных POST с одинаковым name/ID создают разные work_id/каталоги.
  Пять быстрых нажатий в ожидающем UI должны отправить один POST; сервер не обещает
  дедупликацию независимых запросов и не использует name как ключ.
- Разорвать связь после начала POST, затем восстановить соединение: UI сохраняет
  подборку, показывает неизвестный результат и предупреждение, снимает блокировки.
  Автоматических повторов, polling и восстановления нет. Явное новое создание
  запускает отдельный POST; предыдущее могло завершиться, дубли по содержимому допустимы.
- Неизвестный UUID/удалённый материал/отсутствующий archive — 404, без нового экспорта.
  Локальные пути и трассировки не попадают в ErrorResponse.

### Файловый Range и прямой просмотр PDF

Для известного существующего файла размером больше 12 байт проверить будущие исходы
FileResponse Starlette 1.10.0. Обычный Fetch UI не посылает Range, прямой PDF-просмотр
в отдельной вкладке может посылать Range самостоятельно.

| Запрос к выданному URL | Ожидаемый ответ |
| --- | --- |
| GET без Range | 200, полный исходный файл |
| Range: bytes=0-3 | 206, четыре байта, Content-Range |
| Range: bytes=0-3,8-11 | multipart/byteranges 206, Content-Range в частях, не общий |
| Range: items=0-3 или bytes= | 400 text/plain; charset=utf-8, не ErrorResponse |
| Range: bytes=N- при размере N | 416 text/plain; charset=utf-8, пустое тело, Content-Range bytes */N |
| Корректный Range + несовпавший If-Range | Полный 200 |

Текстовые 400/416 возникают только после разрешения готового файла и передачи
управления FileResponse. Отсутствующий файл с любым Range, включая некорректный,
по-прежнему даёт JSON 404 `not_found`; неверный JSON POST даёт JSON 400 `invalid_request`.
Сравнить эти случаи, чтобы исключение не стало глобальным отказом от ErrorResponse.

Оборвать тело после заголовков: JSON вместо остатка файла не добавляется, UI не
предлагает частичный Blob как полный. Затем явный GET без Range получает тот же
сохранённый файл. Для всех этих GET проверить ноль вызовов экспорта и отсутствие
новых каталогов работ. Это будущая приёмка приложения, не уже пройденные проверки.

## 7. Перезапуск и статическая граница

Сохранить известные work_id/URL, корректно остановить и запустить сервер с тем же origin
и var/works. Метаданные и все материалы должны совпасть; сетевой доступ к Полякову
для этого не нужен. Вручную удалить один материал: его GET даёт 404, другие доступны.
Удаление каталога/маркера — 404 для работы. История и восстановление подборки после
перезагрузки страницы не требуются.

Проверить, что UI открывается на `/`, assets — на `/assets/`, а `.specify`, `specs`,
`var/works` и произвольные локальные файлы не выдаются. Неизвестный API URL возвращает
JSON-ошибку, не index.html. Во время долгого экспорта поиск и уже готовое скачивание
должны обслуживаться независимо от лимитера экспорта.

## 8. Регрессии и фиксация фактических результатов

Для автономных тестов API:

```bash
.venv/bin/python -m pytest -q
.venv/bin/python -m ruff check app tests
.venv/bin/python -m pytest -q -m controlled
.venv/bin/python -m pytest -q -m real_local
.venv/bin/python -m pytest -q -s -m live_api tests/live/test_api_live.py
```

В `practices/practice_03/homework/` отдельно выполнить существующие `make check`
и, при доступном источнике, `make demo`. Проверить четыре MCP-инструмента,
прежний output_path и поля результата, PDF/ZIP и ошибочный сценарий через MCP.
Планируемый HTTP-сквозной сценарий охватывает категории → поиск → порядок ID →
создание → ученический результат → отдельные answers/sources, обе ветки PDF/ZIP.

Для каждого реального запуска фиксировать команду/шаги, окружение, результат,
наблюдавшиеся ограничения и фактически созданные артефакты. Не переносить исторические
«33 passed» или синтетические примеры в отчёт как новый результат API.

При уточнении контракта отдельно выполнена диагностика библиотеки FileResponse
во временном окружении: полный 200, одиночный/multipart 206, два текстовых 400
и пустой 416 подтверждены фактически; подробности — research.md, R-09.
Приложение, его тесты, исходный экспортёр и MCP тем историческим прогоном не проверялись.
В этапе реализации они проверены отдельно: автономные CONTROLLED/REAL-LOCAL,
LIVE-API с настоящим сайтом и процессом HTTP, существующие make check/make demo ДЗ 3.
Точные исходы, журналы, UUID и ограничения находятся в api-verification.md.
Проверки, требующие настоящего UI, этим этапом не закрыты.
