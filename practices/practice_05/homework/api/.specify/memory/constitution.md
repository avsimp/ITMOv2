# ДЗ 5 — локальный интерфейс к подборщику задач Constitution

## Core Principles

### I. Сначала требования и согласование

До написания кода соответствующей функции команды ОБЯЗАНЫ зафиксировать требования,
критерии приёмки и согласовать относящуюся к функции часть общего API-контракта.
Изменение требований, затрагивающее взаимодействие UI и API, сначала отражается
в согласованных документах и только затем реализуется. Это исключает разработку
компонентов на несовместимых предположениях.

### II. Переиспользование и совместимость MCP

Локальный интерфейс ОБЯЗАН переиспользовать существующие поиск и экспорт подборщика
из `practices/practice_03/homework/` относительно корня репозитория.
Дублирование их предметной логики в UI или API недопустимо. Изменения ОБЯЗАНЫ сохранять
работоспособность существующего MCP и его инструментов; новый интерфейс не заменяет
действующий MCP-сценарий. При изменении общего кода его совместимость проверяется
через существующий MCP-вход.

### III. Целостность условий и порядка задач

Оригинальные условия, включая рисунки, таблицы и приложения, ОБЯЗАНЫ сохраняться
без содержательных изменений. Согласованный пользователем порядок выбранных задач
ОБЯЗАН совпадать в подборке и экспортируемых материалах; скрытая перестановка запрещена.
Блок 19–21 ОБЯЗАН оставаться одним пунктом с общим условием и тремя вопросами:
в подсчёте, нумерации, отображении и экспорте его нельзя разбивать на три задачи.
Допустимо существующее техническое переименование ссылок на приложения при экспорте,
если исходное условие и связь с оригинальными файлами сохранены в источниках.

### IV. Отделение ученических материалов

Материалы для передачи ученику ОБЯЗАНЫ содержать только условия и необходимые
приложения. Ответы и сведения об источниках ОБЯЗАНЫ храниться и выдаваться отдельно
от ученических файлов; они не включаются в ученический PDF или ZIP. Это разделение
ОБЯЗАНО сохраняться при отображении, экспорте и передаче файлов через новый интерфейс.

### V. Единый контракт и ответственность команд

Обе команды ОБЯЗАНЫ использовать один контракт `../contracts/api-v1.yaml`
(относительно корней `api/` и `ui/`). Это единственный источник соглашений о запросах,
ответах, ошибках и передаче результатов экспорта. Независимые расходящиеся версии
контракта в компонентах запрещены.

Команда UI отвечает за свой компонент. Команда API отвечает за свой компонент,
ведение общего контракта и интеграцию UI с API и существующим подборщиком.
Любое изменение контракта ОБЯЗАНО быть согласовано обеими командами до реализации
зависящего от него кода. Команда API фиксирует согласованное изменение в общем файле;
единоличное владение файлом не заменяет согласование.

### VI. Успешные, ошибочные и сквозные проверки

Критерии приёмки каждого реализуемого сценария ОБЯЗАНЫ включать успешный путь
и обработку ошибки. Завершённый интеграционный этап ОБЯЗАН включать сквозную проверку
от действия в UI через API до существующего подборщика и наблюдаемого результата.
Для экспорта проверяются состав ученических материалов, отделение ответов и источников,
порядок задач и учёт блока 19–21 как одного пункта. Проверки соответствия общему контракту
и сохранения работоспособности MCP обязательны для затрагивающих их изменений.

### VII. Только фактические результаты

Отчёты, доказательства проверки и сообщения о готовности ОБЯЗАНЫ отражать только
фактически выполненные действия и наблюдавшиеся результаты. Для выполненной проверки
фиксируются команда или воспроизводимые шаги, результат и относящиеся к нему артефакты,
если они созданы. План, ожидание, результат на заглушке и непроверенное предположение
нельзя выдавать за успешную проверку работающей интеграции. Невыполненные, заблокированные
и неуспешные проверки явно обозначаются своим фактическим статусом.

## Границы проекта и совместной работы

Проект ДЗ 5 — локальный интерфейс к существующему подборщику задач из ДЗ 3.
Корень совместной работы — `practices/practice_05/homework/`; компоненты находятся
в `ui/` и `api/`, общий контракт — в `contracts/api-v1.yaml`.
Настоящая конституция находится в API-проекте и определяет правила его работы
и взаимодействия с командой UI.

Команды ОБЯЗАНЫ согласовывать изменения за границами своего компонента до редактирования.
Изменения общего кода подборщика ОБЯЗАНЫ сохранять правила исходных материалов,
экспорта и MCP, перечисленные выше. Принятие конституции фиксирует правила;
оно не разрешает переход к коду без требований и согласованного контракта.

## Порядок разработки и фиксации этапов

1. Зафиксировать требования и проверяемые критерии приёмки этапа.
2. Согласовать общий контракт между UI и API; при изменении сначала обновить его
   согласованную редакцию и только затем реализовывать зависимые изменения.
3. Реализовать компоненты в пределах ответственности команд и выполнить проверки этапа.
4. Зафиксировать фактические результаты. Чат UI сообщает чату API о готовности своих
   файлов, перечисляет их и сообщает результаты проверок.
5. Локальные коммиты завершённых этапов выполняет только чат API. Перед коммитом
   чат API ОБЯЗАН получить подтверждение, что второй чат завершил редактирование
   и не редактирует файлы во время подготовки и выполнения коммита.
6. Чат API проверяет статус и diff и включает в коммит только относящиеся к завершённому
   этапу изменения. Несвязанные или незавершённые изменения в коммит не включаются.
7. Работа и коммиты выполняются в текущей ветке; создание или переключение ветки
   в рамках этого процесса запрещено. Отправка на GitHub выполняется только
   по отдельному явному запросу пользователя.

## Governance

Эта конституция обязательна для требований, планов, реализации, проверки и фиксации
этапов API-проекта и его взаимодействия с UI. При противоречии рабочего документа
конституции документ ОБЯЗАН быть приведён в соответствие до реализации.

Поправка ОБЯЗАНА содержать причину, точное изменение правил и оценку влияния
на требования, контракт, компоненты и проверки. Поправка принимается после явного
согласования пользователем; изменения совместных правил также доводятся до обеих
команд до применения. При необходимости фиксируется порядок перехода на новые правила.

Версия конституции следует SemVer: MAJOR — несовместимое переопределение или удаление
правила; MINOR — новый принцип, раздел или существенное расширение требований;
PATCH — уточнение формулировок без изменения смысла. При каждой принятой поправке
обновляются версия и дата последнего изменения; исходная дата принятия сохраняется.
Версия `1.0.0` обозначает первое принятие этой конституции.

Перед началом реализации, при согласовании изменения контракта и перед коммитом этапа
чат API ОБЯЗАН проверить соответствие этим принципам. Чат UI подтверждает соответствие
своего компонента при сообщении о готовности. Несоответствие устраняется до объявления
этапа завершённым либо сначала принимается согласованная поправка к конституции.
