# Рефлексия по ДЗ 5

## Основание и результат

Работа эмулировала две команды в двух чатах: UI описывал действия, состояния и ошибки,
API — данные, правила и HTTP-слой существующего подборщика из ДЗ 3. Для обеих сторон
использован **Spec Kit**. Сначала сохранены независимые спецификации, затем согласованы
общий контракт и изменения требований, после этого реализованы UI/API и сквозные проверки.

Этот текст опирается на [соглашения](evidence/agreements.md),
[сравнение API до/после](evidence/api-comparison.md),
[сравнение UI до/после](evidence/ui-comparison.md),
[API verification](evidence/api-verification.md),
[UI verification](evidence/ui-verification.md) и прямое наблюдение пользователя ниже.
Сравнение OpenSpec основано на этапах [материалов практики 5](../prenetation.pdf),
а не на вымышленном втором прохождении этой же фичи или замерах эффективности.

## Какие решения действительно пришлось согласовать

- **Создание — один длительный POST, успех только после готовности.** Это позволило
  не вводить фоновые задания и polling, но потребовало различать pending, failed и unknown.
  Поиск во время ожидания остаётся доступен; редактирование отправленной подборки заблокировано.
- **Потеря подтверждения не равна отказу сервера.** UI сохраняет подборку и предупреждение,
  не повторяет создание из JS. Явное «Создать новую работу» — новый запрос с возможным дублем;
  восстановление неизвестного ID контракт не предоставляет.
- **Имя не определяет идентичность.** Оно необязательно, при отсутствии его назначает сервер;
  каждое создание получает отдельные UUID/каталог. Имя не заменяет путь или ключ идемпотентности.
- **Граница браузера и диска.** UI получает серверные URL, не абсолютные локальные пути;
  HTML-проекция сохраняет условия/ресурсы, ответы не попадают в поиск. Ученический результат —
  PDF либо ZIP с приложениями, ответы и sources выдаются отдельно.
- **Хранение не равно истории интерфейса.** Готовые материалы доступны после перезапуска,
  но подборка в странице и потерянный work_id не восстанавливаются автоматически.
- **Транспортные детали стали частью соглашения.** Точный POST работает без redirect,
  вариант со слешем отклоняется; прикладные ошибки JSON не смешиваются с текстовыми
  Range-400/416 файлового транспорта. Эти детали влияли на корректное поведение UI.

Польза двух спецификаций проявилась в том, что UI не мог сам придумать восстановление,
а API — считать выдачу файла достаточной без пользовательских состояний и разделения материалов.
Единственный YAML и решения A-01–08 дали обеим сторонам общую точку проверки до кода.

## Что показали проверки и окончательное решение

В отчётах разделены CONTROLLED, REAL-LOCAL и LIVE: успешная подмена API не доказывает
работу настоящего сайта, а работа локального экспортёра с фиксированным внешним HTTP
не заменяет живую браузерную интеграцию. Для PDF/ZIP подтверждены реальные сквозные
сценарии, для ошибок — offline-поиск, unknown после заголовков и отдельные отказы файлов.

При этом обнаружилась **B-01**: Chromium при определённом разрыве TCP до заголовков
транспортно отправил два POST внутри одного Fetch. Это важное различие между
«JS не вызывает retry» и «сервер исполнит ровно один раз». Последнее без идемпотентности
обещать нельзя. Успешный обрыв после заголовков не закрывает этот другой сценарий.

Пользователь в **A-09 от 2026-10-28** явно ограничил учебную приёмку Chromium и отсутствием
автоповтора в JS. B-01 оставлен известным ограничением без новых полей/механизмов и кода;
Firefox, не прошедший запуск, исключён из обязательной приёмки. Это решение об объёме
сдачи, не исправление дефекта и не успешная проверка Firefox. Снимки и прежние отчёты
сохранены, чтобы изменение границ оставалось видимым.

## Наблюдаемые этапы Spec Kit и OpenSpec

| Этап | Spec Kit в артефактах этого ДЗ | OpenSpec в материалах практики |
| --- | --- | --- |
| Намерение и границы | Отдельные конституции и spec.md UI/API с историями, FR/SC и уточнениями | Explore и proposal/specs: цель, условия, ошибки, сохраняемое поведение |
| Уточнение человеком | Решения A-01–08, сверка UI/API, единый контракт, снимки до/после до кода | Review, при необходимости update-change; человек принимает решения до apply |
| Дизайн и задачи | plan.md, research.md, data-model.md, quickstart.md и подробные tasks.md | Design при необходимости и tasks внутри изменения |
| Реализация и проверка | Код по согласованным требованиям, отмеченные задачи, раздельные отчёты и сквозные результаты | Apply, tests/diff и приёмка человеком; при новых фактах возврат к уточнению |
| Фиксация результата | В этом ДЗ — Git-коммиты, исторические снимки/отчёты и актуальное дополнение A-09 | Sync принятых требований в main specs и archive завершённого change |

В этом ДЗ Spec Kit дал подробную прослеживаемость требований к задачам двух сторон.
Цена видна в необходимости поддерживать согласованность многих документов и передач.
OpenSpec в учебном маршруте организует работу вокруг изменения с последующим sync/archive;
это иная форма хранения результата, но тоже требует решений человека и фактических тестов.
Проверка структуры документов в обоих подходах сама по себе не доказывает работу приложения.

Из имеющихся материалов нельзя заключить, что один инструмент быстрее или дешевле
другого в определённое число раз. В этой работе нет сопоставимых замеров времени/токенов
и двух одинаковых реализаций через оба процесса. Отдельный OpenSpec sync/archive для ДЗ 5
не выполнялся: его артефакты ведутся через Spec Kit и Git.

## Затраты двух чатов и что стоило сделать раньше

**Наблюдение пользователя:** работа двумя чатами оказалась слишком долгой и
токенозатратной; следовало раньше ограничить объём проверок. Числовых замеров для
оценки затрат нет, поэтому это качественное наблюдение, а не измеренный результат.

Отчёты показывают, куда расширился объём: отдельные наборы двух сторон, повторные
живые PDF/ZIP, детальная диагностика разрывов TCP, попытки запуска Firefox и много
финальных gates. Часть этой работы нашла реальные границы, но учебная цель не требовала
бесконечно продолжать исследование после получения достаточных сквозных свидетельств.

Для похожей задачи полезно заранее зафиксировать:

1. Один поддерживаемый браузер и точный уровень обещаний при сетевых отказах.
2. Минимальный набор приёмки: основной PDF/ZIP, один реальный ошибочный путь,
   контролируемые лимиты и необходимая регрессия переиспользуемого кода.
3. Одного владельца общих сквозных проверок и единый итоговый отчёт; второй чат
   использует полученные свидетельства с указанием источника вместо дублирования прогонов.
4. Условие остановки: после достаточных результатов — фиксация известных ограничений
   и упаковка, дальнейшее расширение проверок только по отдельному решению.

Главный вывод: согласование контракта до кода было полезным, но самого SDD-процесса
недостаточно для экономии. Нужны ранние границы приёмки и проверки, соразмерные учебной
задаче. Итоговое решение A-09 и отдельная упаковка уже полученных результатов реализуют
именно этот вывод. Текущий комплект и ограничения сведены в
[final-status.md](evidence/final-status.md), запуск и короткое демо — в [README.md](README.md).
