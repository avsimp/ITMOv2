## Format: `[ID] [P?] [Story] Description`

- T001–T053 — уникальные последовательные ID; незаполненный checkbox означает невыполненную задачу.
- `[US1]`, `[US2]`, `[US3]` — истории текущей UI-спецификации, не номера историй API.
- `[P]` — независимые файлы после выполнения явно указанных предпосылок; это возможность
  параллельной работы, не команда запуска агентов или разрешение редактировать общий файл.
- Тесты в начале истории подготовить до реализации, подтвердить отсутствие нужного
  поведения, затем получить успешный прогон; ошибка окружения не заменяет проверку поведения.

## Path Conventions

- Пути задач `index.html`, `assets/`, `tests/`, `pytest.ini`, `README.md`, `specs/`
  отсчитываются от `practices/practice_05/homework/ui/`.
- `../api/`, `../contracts/`, `../evidence/` — соседние каталоги homework.
- `../../../practice_03/homework/` от корня UI — существующий подборщик ДЗ 3.
- Создаваемые в будущем файлы приложения и тестов перечислены как назначения задач,
  а не как уже существующие артефакты. HTML/CSS/JS без frontend-фреймворка и сборки.
- `tests/test_ui.py` остаётся точкой настоящей браузерной интеграции из plan.md;
  изолированные проверки разнесены по `tests/test_*.py`, чтобы не редактировать один файл параллельно.
- UI не меняет `../api/app/`, общий YAML или исходный подборщик вместо команды API.
  UI ведёт собственные `../evidence/ui-*.md`; общие журналы `ui-api-live.md`
  и `ui-api-faults.md` из задач API остаются под ответственностью API.

### Уровни проверки и правила зачёта

| Метка | Что проверяется | Подмены и ограничения |
| --- | --- | --- |
| CONTROLLED | Настоящие файлы UI, браузер, обработчики и клиентское состояние | API/ресурсы/файлы воспроизводятся Playwright-перехватами; ответ обязан соответствовать единственному YAML, кроме явно негативных фикстур; это не настоящий API/Bank/export |
| LIVE-UI | Настоящий UI → настоящий HTTP API → исходные Bank/export_pdf → файлы, включая сайт Полякова | Нет route.fulfill, fake API, dependency overrides или подмены источника; требуются готовность API и сеть; транспортный отказ вводится реальным отключением/разрывом и явно описывается |
| Результаты API | CONTROLLED / REAL-LOCAL / LIVE-API / MCP по отчётам команды API | Записанный HTTP-источник REAL-LOCAL остаётся подменой внешнего источника; эти отчёты дополняют, но не заменяют собственный LIVE-UI |

Проверки со схемами подменённых ответов доказывают формат фикстуры и реакцию UI,
не соответствие фактических ответов сервера. Последнее проверяется отдельно на LIVE-UI.
Сеть/готовность API не заменять подменой с сохранением названия реального прогона.
При блокере записать причину и оставить задачу незавершённой, не засчитывать skip как успех.
Журнал каждого запуска содержит уровень, команду/шаги, окружение/браузер, версию контракта,
реальные ID/work_id, наблюдаемый исход и только фактически полученные артефакты.

### Within Each User Story

1. Подготовить изолированные контрактные и негативные тесты до реализации поведения.
2. Реализовать состояние → HTTP/ресурсы → DOM/обработчики, не меняя соседние области store.
3. Получить успешный CONTROLLED-прогон и отдельно сообщить о готовности к интеграции.
4. После межкомандных gates выполнить LIVE-UI без перехвата ответов; записать реальный исход.
5. При недоступности внешней зависимости сохранить незавершённую задачу и блокер.

## Implementation Strategy

### MVP First (User Story 1 Only)

1. До реализации пройти `/speckit.analyze` по spec/plan/tasks/контракту 1.0.0.
2. Выполнить Setup/Foundation T001–T008 и US1 T009–T016.
3. Передать работающие файлы поиска API в T017; это UI-MVP для просмотра банка.
4. После API-D1 провести T018/T019 и checkpoint T020.
5. MVP не включает составление и экспорт; полной сдачей ДЗ 5 считается только весь цикл.

### Incremental Delivery

1. Общая основа → US1 → полезный поиск оригинальных условий.
2. US2 → независимая от выдачи упорядоченная подборка без дублей.
3. US3 → создание/материалы, корректные отказы/unknown и настоящий PDF/ZIP.
4. Общие контрактные/браузерные проверки и подтверждение регрессий MCP → итоговая приёмка.
5. После каждого изменения проверять затронутое поведение; повторно выполнять более широкую
   проверку при новом изменении/ошибке, а не без причины. Фактические результаты фиксируются отдельно.

### Parallel Team Strategy

UI владеет index/assets/tests своего проекта; API — своим сервером, общим контрактом,
интеграцией с ДЗ 3 и регрессиями MCP. Контролируемые сценарии позволяют разрабатывать
независимо, но не снимают gates настоящего взаимодействия. Передача готовности по частям
устраняет циклическое ожидание. Состояния code-ready, CONTROLLED-pass и LIVE-UI-pass
сообщаются раздельно; коммит завершённого этапа делает API после остановки редактирования UI.
