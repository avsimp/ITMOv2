# Quickstart: запуск и проверка UI

**Дизайн**: 2026-10-27. **Реализация и проверки**: 2026-10-28.
UI реализован. Фактические результаты — в [ui-verification.md](../../../evidence/ui-verification.md);

## 1. Условия начала проверки

- Общий контракт уже принят как 1.0.0/agreed; UI подтвердил A-01–08 и закрыл
  API-Q01–04 в contract-review. Окончательная спецификация —
  [ui-after.md](../../../evidence/ui-after.md).
- Реализованы `ui/index.html`, `ui/assets/`, API-приложение и тесты согласно планам.
- API имеет Python 3.11+, закреплённые зависимости исходного экспортёра, FastAPI/Uvicorn,
  pytest и Python Playwright; Chromium установлен. Точные версии фиксируются при запуске.
- Для живых поиска/экспорта доступен источник Полякова. Для ошибок/гонок используются
  контролируемые ответы будущих Playwright-тестов; их успех не считается живой интеграцией.
- Один worker API, без --reload во время долгого создания, origin совпадает с настройкой URL.

## 2. Запуск после появления реализации

Из `practices/practice_05/homework/api/` выполнить команды, предложенные планом API:

```bash
uv venv .venv
uv pip sync --python .venv/bin/python requirements-dev.txt
.venv/bin/python -m playwright install chromium
.venv/bin/python -m uvicorn app.main:app --host 127.0.0.1 --port 8000 --workers 1
```

Для браузерных проверок окружение должно также содержать pytest и Playwright.
Для дополнительной проверки Firefox установить `.venv/bin/python -m playwright install firefox`;
в текущем окружении после загрузки браузера остаётся ошибка запуска профиля,
поэтому результат Firefox не объявлен успешным.
Отдельный frontend-пакетный менеджер или UI dev-сервер не нужен. Открыть
`http://127.0.0.1:8000/`, в Network проверить `/assets/styles.css`, модули JS и
`/api/v1`. Не открывать index.html через file:// и не запускать общий файловый сервер
на весь каталог ui. Спецификации и `.specify/.opencode` не должны выдаваться как статика.

При смене порта согласованно настроить origin API, открыть новый адрес и убедиться,
что запросы/выданные URL не остались на жёстко заданном 8000.

## 3. Поиск, ресурсы, пагинация

1. Проверить начальное приглашение выбрать номер и недоступность поиска/создания.
2. Выбрать номер 5, дождаться категорий, оставить «Все» и явно запустить поиск.
   В запросе нет пустого category_ids; одна выбранная категория — один положительный ID.
3. Сверить карточку с оригиналом: полный текст, таблицы, sub/sup, рисунки, ссылки,
   ID, номер и признак приложений. В JSON/DOM нет answer/answer_html или просмотра ответа.
4. Выбрать «19–21»: отправлен 19, общая игра с тремя вопросами — одна карточка.
5. Пройти три порции вперёд и назад; «Следующие» следует next_offset, конец по null,
   «Предыдущие» на первой странице недоступно. Показаны total и диапазон, не обещан
   неизменный снимок живого банка.
6. На контролируемом наборе получить пустую выдачу, затем 422 и 502/504. Пустота
   отличается от ошибок; доступны понятные сообщения и явный повтор.
7. Задержать ответ поиска A, сменить фильтр и выполнить B, вернуть B раньше A.
   Ни поздний результат, ни ошибка/finally A не меняют выдачу/занятость B.
8. Оборвать отдельный GET изображения: карточка отмечена неполной и недоступна
   для добавления; повтор ресурса не запускает экспорт. SVG используется только img.

## 4. Подборка и сохранение порядка

1. Добавить A, B и полный блок C=19–21 из разных страниц/номеров. Пять попыток
   повторно добавить A оставляют один экземпляр.
2. У C нажать «Вверх», затем удалить A: остаются C, B, номера 1 и 2.
   Крайние движения недоступны, повторное добавление A помещает её в конец.
3. Сменить фильтр, просмотреть следующие результаты, получить пустоту и ошибку:
   состав/порядок подборки сохранён. Кнопки карточек правильно показывают «В подборке».
4. Проверить 0/1/100 пунктов и попытку 101-го; пустая работа не создаётся,
   один блок всегда считается одним пунктом. Это проверяется контролируемыми данными,
   а не поиском ста случайных живых задач ради лимита.
5. Все действия выполнить с клавиатуры; фокус после удаления/перемещения остаётся
   осмысленным, статусы доступны текстом, не только цветом.

## 5. Сквозной PDF без приложений

Выбрать реально доступные задачи без приложений, включая рисунок и игру;
ID из примеров контракта синтетические или исторические, не гарантируются живым сайтом.

1. Создать без имени и пути. В Network один POST с topic_ids в пользовательском порядке.
   Пять быстрых нажатий до ответа не отправляют дополнительные POST.
2. Пока запрос ожидается, создание/изменение подборки заблокированы, поиск и материалы
   предыдущей известной работы доступны. Нет polling, job_id, прогресса или отмены.
3. После 201 показаны серверное имя и count, result PDF/student, archive=null,
   отдельные преподавательские действия. Блокировки сняты не позднее 1 секунды.
4. Получить result отдельным GET. После полного тела доступна ссылка сохранения
   с Artifact.filename; UI не утверждает запись на диск. Сохранить файл вручную.
5. Получить answers и sources отдельно; успешный JSON sources не считается ошибкой.
   Сверить порядок/нумерацию, три ответа блока в одном пункте, отсутствие ответов
   и служебных источников в ученическом PDF. Визуально просмотреть рисунки/таблицы.
6. Повторить GET того же result: сохранённые байты совпадают, новых POST нет.
   Изменить подборку: прежний материал помечен «Для предыдущей подборки».

## 6. Сквозной ZIP с приложениями

1. Создать работу с подтверждённой задачей с приложением и блоком 19–21.
2. Основной result — ZIP/student, archive не null, pdf — отдельный preview.
   Кнопка ученика не использует preview PDF вместо ZIP.
3. Скачать ZIP, распаковать целиком в другой каталог. Внутри только work.pdf
   и work.files с необходимыми приложениями; answers/sources снаружи.
4. Сверить относительные ссылки, порядок пунктов и имена приложений по позициям.
   PDF внутри архива совпадает с preview; result/архив совпадают по байтам.
5. Проверить, что снимок выбора перед POST совпадает с Work.topic_ids и готовым комплектом.

## 7. Подтверждённый отказ и неизвестный исход

На контролируемом сервере/в браузерных перехватах проверить отдельно:

- POST возвращает валидный 422/409/500/502/504 ErrorResponse: UI показывает подтверждённую
  причину, сохраняет подборку, снимает блокировки и допускает явное исправление/повтор.
  409 не предлагается исправлять уникальным именем, а 504 не означает клиентский deadline.
- Разорвать связь после начала POST до подтверждённого ответа; затем вернуть сеть.
  UI показывает «Результат не подтверждён» и «Предыдущая работа могла быть создана»,
  снимает блокировки. Подборка и известные материалы сохранены, автоматических POST — ноль.
- В unknown поискать, добавить, удалить и переставить задачи: действия доступны,
  предупреждение остаётся. При пустой подборке новое создание недоступно.
- Явно нажать «Создать новую работу» при допустимой подборке: ровно один новый POST,
  новый снимок ID, снова блокировка ожидания. Дубль содержимого допустим, поиска
  или восстановления потерянной работы нет, это не повтор GET.
- Вернуть оборванный или некорректный успешный ответ POST: успех не объявляется,
  неизвестный исход не превращается в подтверждённый отказ или автоматический retry.
- Проверить A-07: точный POST `/api/v1/works` обслуживается без redirect и вызывает
  экспорт один раз; `/api/v1/works/` даёт JSON 404 not_found без Location и ноль экспортов,
  в том числе у диагностического клиента со следованием redirect. При навязанном
  307/308 браузерный UI с `redirect: "error"` не отправляет второй POST и не повторяет
  создание автоматически. Это будущий сценарий, не результат выполненного вызова.

## 8. Ошибки файлов и сохранность после перезапуска

- GET материала возвращает 404 ErrorResponse: сообщение у конкретного файла,
  другие файлы и подборка доступны. Повтор — GET, новых POST нет.
- Оборвать тело GET после заголовков: нет частичного Blob-сохранения; UI показывает
  ошибку передачи, допускает явный повтор. Известная работа не переходит в unknown.
- После получения другого Blob старая локальная ссылка освобождена; основной серверный
  URL остаётся доступным. Не заявлять тестом браузера успешность записи на диск.
- Оставить страницу с известным Work открытой, перезапустить API с тем же origin
  и сохранённым хранилищем. Метаданные и скачивания доступны с прежними байтами,
  источник для повторного скачивания не нужен.
- Вручную удалить один материал: понятный 404 только для него, без экспорта заново.
  После перезагрузки страницы не требовать восстановления подборки, ID или истории.
- Проверить A-08 на согласованном baseline FastAPI 0.162.0 / Starlette 1.10.0:
  обычное скачивание UI не отправляет Range/If-Range и получает полный 200.
  Прямой просмотр PDF допускает 206 одного диапазона с Content-Range и multipart 206
  с Content-Range внутри частей, без общего заголовка.
- Диагностический GET существующего материала с некорректным Range даёт транспортный
  400 text/plain; недостижимый диапазон — 416 text/plain с пустым телом и
  Content-Range bytes */N. UI не пытается разобрать их как JSON; при неожиданном таком
  ответе обычного скачивания — ошибка получения и явный GET, без POST/частичного Blob.
- Для отсутствующего материала даже с плохим Range ожидается JSON 404 до FileResponse;
  неверный JSON POST даёт JSON 400. Эти прикладные отказы не становятся текстовыми.
  Несовпавший If-Range или более 100 диапазонов — полный 200 по контракту.

## 9. Автоматизированная проверка и отчёт

Тесты реализованы. Из каталога UI (каждый запуск поднимает свой API и изолированное storage):

```bash
../api/.venv/bin/python -m pytest -q -m controlled
../api/.venv/bin/python -m pytest -q -m real_local
../api/.venv/bin/python -m pytest tests/test_ui.py -q -s -m live_ui
../api/.venv/bin/python -m pytest tests/test_ui.py -q -s -m boundary_probe
```

Контролируемые сценарии Playwright проверяют ошибки, гонки, блокировки и лимиты;
`real_local` использует настоящий UI/API/Bank/export_pdf, заменяя только сырой внешний
HTTP-источник; это воспроизводимая проверка SC-002, не живой сайт.
сквозные сценарии с реальным API/Bank/export выполняются отдельно без перехватов
и явно помечаются в отчёте. Команды API-тестов и существующих регрессий MCP —
в API quickstart; их выполняет команда API после затрагивающих интеграцию изменений.

Фиксировать фактическую команду/шаги, версию браузера, версию контракта, выбранные ID,
наблюдаемый исход и доступные PDF/ZIP/логи. Результат заглушки не доказывает работу
реального источника, отсутствие живой сети отмечается блокером соответствующего сценария.

`boundary_probe` — отдельный известный непройденный сценарий разрыва до заголовков:
в Chromium наблюдается транспортная повторная отправка при одном Fetch и две работы
на сервере. Он не помечен xfail и не включается в успешный счётчик controlled/live_ui.
Подробное воспроизведение и вопрос к API — в ui-verification.md. В обычном `live_ui`
проверяется реальный разрыв после заголовков, до полного JSON: unknown и отсутствие retry.
