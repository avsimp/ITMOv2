# ДЗ 5 — локальный интерфейс к подборщику задач Constitution

## Core Principles

### I. Требования и общий контракт до кода

Перед реализацией каждого этапа команды обязаны зафиксировать требования, критерии приёмки
и согласованный контракт взаимодействия. Обе команды используют единственный общий контракт
`../contracts/api-v1.yaml`, путь к которому одинаков относительно каталогов `ui/` и `api/`.
Независимые копии контракта не допускаются. Любые изменения контракта согласуются между UI
и API и отражаются в общем файле до реализации затронутых частей. Это исключает разработку
по несовместимым предположениям.

### II. Переиспользование подборщика и совместимость MCP

Локальный интерфейс обязан переиспользовать существующие поиск и экспорт из ДЗ 3.
Дублирование их предметной логики в UI или новой API-обвязке не допускается.
Изменения обязаны сохранять работоспособность существующего MCP: его инструменты,
сценарии поиска и экспорта должны продолжать работать. Этап, затрагивающий общий механизм,
не считается завершённым без проверки соответствующих MCP-сценариев.

### III. Сохранность условий, порядка и блока 19–21

Оригинальные условия задач, включая рисунки, таблицы и связанные материалы, обязаны
сохраняться без пересказа, сокращения и подмены. Существующие правила экспорта приложений
сохраняются; оригиналы условий и ссылок остаются в источниках. Порядок задач в подборке
должен сохраняться при передаче между UI, API и экспортом. Изменение порядка допустимо
только как явное действие пользователя. Блок 19–21 с общим условием и тремя вопросами
всегда считается одним пунктом: в подборке, нумерации, подсчёте и экспорте.

### IV. Разделение ученических и служебных материалов

Ученические материалы обязаны быть отделены от ответов и источников. В предназначенные
ученику PDF, ZIP и приложения запрещено включать ключи ответов и служебные файлы
источников. Ответы и источники сохраняются отдельно для преподавателя; UI и API обязаны
явно различать назначение выдаваемых материалов. Так сохраняется существующее разделение
ученического задания и преподавательского комплекта.

### V. Проверяемость и фактические результаты

Проверки каждого реализованного этапа обязаны включать успешный и ошибочный сценарии.
Приёмка интеграции обязана включать сквозной сценарий от действия в UI через API
и существующий подборщик до результата экспорта. Проверки должны подтверждать соблюдение
контракта, сохранность условий и порядка, правило блока 19–21 и разделение материалов.
В отчёты и свидетельства записываются только фактически выполненные действия и полученные
результаты с указанием команды или шагов, наблюдаемого исхода и доступного артефакта.
Невыполненные и заблокированные проверки обозначаются явно; ожидаемый результат,
план или ответ заглушки запрещено выдавать за подтверждённую работу интеграции.

## Границы проекта и ответственность команд

ДЗ 5 — локальный интерфейс к существующему подборщику задач:
`practices/practice_03/homework/` относительно корня репозитория.
Рабочая область ДЗ 5 — `practices/practice_05/homework/`; текущий проект UI расположен
в её каталоге `ui/`. Эти правила определяют взаимодействие UI и API при работе над ДЗ 5.

- Команда UI отвечает за свой компонент в `ui/`, его соответствие общему контракту,
  проверки своего компонента и передачу фактического статуса готовности.
- Команда API отвечает за свой компонент в `api/`, ведение общего контракта
  в `contracts/api-v1.yaml` и интеграцию с UI и существующим подборщиком.
- Ответственность API за контракт не отменяет обязательного согласования его изменений
  с UI до реализации. Команды согласуют изменения, затрагивающие границы компонентов.
- Изменения существующего подборщика допустимы только в рамках согласованных требований
  и с сохранением правил переиспользования, содержимого материалов и совместимости MCP.

## Порядок работы и фиксации этапов

1. До кода зафиксировать требования этапа, критерии приёмки и согласованный общий контракт.
2. Реализовать согласованный этап в пределах ответственности команд; при необходимости
   изменения контракта сначала согласовать и обновить его, затем продолжить реализацию.
3. Выполнить применимые успешные, ошибочные и сквозные проверки, а также проверки MCP
   при затрагивании общего механизма. Зафиксировать фактические результаты и ограничения.
4. Чат UI сообщает чату API о готовности своих файлов: указывает их пути, выполненные
   проверки, результаты и наличие блокеров. Сообщение о готовности должно подтверждать,
   что чат UI закончил редактирование передаваемых файлов.
5. Локальные коммиты по завершённым этапам выполняет только чат API. Перед коммитом он
   обязан получить подтверждение, что второй чат не редактирует файлы, проверить состав
   изменений и включить только относящиеся к этапу файлы. Параллельное редактирование
   вторым чатом во время подготовки и выполнения коммита не допускается.
6. Работа ведётся в текущей ветке. Отправка на GitHub выполняется только по отдельному
   запросу пользователя.

## Governance

Конституция имеет приоритет над локальными договорённостями, планами и задачами ДЗ 5.
При расхождении реализация приостанавливается в затронутой части до согласования решения.
Перед началом реализации и при приёмке каждого этапа обе команды обязаны проверить
соответствие требованиям конституции; чат API дополнительно проверяет его перед коммитом.

Поправка оформляется с описанием причины, изменяемых правил и влияния на требования,
контракт и компоненты. Изменения согласуются командами UI и API и утверждаются
пользователем до реализации по новым правилам. В конституции фиксируются новая версия
и дата изменения; связанные требования и контракт приводятся в соответствие до кода.
Временный Sync Impact Report проверяется и удаляется перед коммитом конституции.

Версионирование — SemVer: MAJOR для несовместимого изменения или удаления правил,
MINOR для новых принципов, разделов или существенного расширения требований,
PATCH для уточнений формулировок без изменения смысла. Первоначальное принятие — `1.0.0`.
Дата принятия сохраняется; дата последней поправки обновляется при изменении конституции.
