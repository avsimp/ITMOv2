## Окружение

ОС / CPU / GPU / RAM / VRAM / свободный диск: macOS 26.6.2 (build 25G83) / Apple M5 (10-ядерный GPU, Metal 4, встроенный) / RAM 16 GB, отдельной VRAM нет (unified memory) / свободно на диске ~169 GB из 460 GB.
Ollama или LM Studio / OpenCode / Python, версии: Ollama 0.33.2 / OpenCode 1.18.32 / Python 3.14.4 (учебный код совместим с 3.10+).
Модель, разработчик, семейство, тег и ID: Qwen (Alibaba), семейство qwen35, тег `qwen3.5:4b`, локальный ID `2a654d98e6fb`; кастомизированные варианты `itmo-local` (ID `0679e5723779`, с SYSTEM и temperature 0.2) и `itmo-agent` (ID `6b5eddf34336`, без SYSTEM, num_ctx 65536).
Формат, квантизация, лицензия, источник: формат GGUF, квантизация Q4_K_M, параметры 4.7B, лицензия Apache License 2.0, источник — `ollama.com/library/qwen3.5` (скачано командой `ollama pull qwen3.5:4b`).
Фактический контекст, размещение CPU/GPU: для `itmo-local` — 4096 токенов (ограничен PARAMETER num_ctx в Modelfile), для `itmo-agent` — фактически загружен полный запрошенный контекст 65536 (подтверждено `ollama ps`), размещение 100% GPU (Metal, unified memory на Apple Silicon).
Почему выбрана эта конфигурация: 16 GB RAM соответствуют строке «qwen3.5:4b, контекст 4096» из таблицы подготовки к практике (файл `PREPARATION.md` присутствовал в репозитории на момент выбора модели, коммит `831a1bd`; позже он был удалён из дерева практики апстримом курса — содержимое таблицы доступно через `git show 831a1bd:practices/practice_03/PREPARATION.md`, актуальный `README.md` этой таблицы не содержит); загрузка весов ~3.4 GB оставляет достаточный запас памяти для контекста и работы OpenCode одновременно. Модель поддерживает tool calling и русский язык, что нужно для агентного этапа.

## Эксперимент

Фактор A/B: temperature 0.2 (A) vs 0.8 (B) при трёх фиксированных seed (42, 43, 44).
Неизменные условия: `--mode system` (system.txt как явный `system`-message в каждом запросе), один и тот же вопрос про CI, `num_ctx=4096`, `num_predict=512`, `think=false`, `stream=false`. Файлы серии A (temp=0.2): `lab/results/cold42.json`, `cold43.json`, `cold44.json`. Файлы серии B (temp=0.8): `lab/results/hot42.json`, `hot43.json`, `hot44.json`. Отдельно: `lab/results/system.json` — тот же запрос, что и `cold42.json` (файлы побайтово идентичны, `system.json` создан первым и затем скопирован/переигран как `cold42.json`); `lab/results/baseline.json` — контрольный запуск **без** system-сообщения (тот же вопрос, temp=0.2, seed=42), использован только для сравнения «с system prompt / без», в температурную серию A/B не входит.

**Обнаруженная неточность (при повторном аудите):** поле `request.model` различается внутри серии A — `cold42.json` (= `system.json`) и `baseline.json` содержат `"model": "qwen3.5:4b"`, а `cold43.json` и `cold44.json` содержат `"model": "itmo-local"`. Вся серия B (`hot42.json`, `hot43.json`, `hot44.json`, `hot42-warm-timing.json`) выполнена на `itmo-local`. Ранее в отчёте это различие не было замечено и вся серия A ошибочно описывалась как выполненная на `itmo-local`.
Проверка сопоставимости (ограниченная): явный `system`-message и явные `options.temperature/seed/num_ctx/num_predict` в каждом запросе задавались одинаково для обоих тегов, а `itmo-local` создан из `qwen3.5:4b` добавлением в Modelfile тех же `num_ctx`/`temperature`/`SYSTEM`, что и так передаются в запросе явно. Один контрольный повторный запрос (temp=0.2, seed=42, тот же текст вопроса и system prompt), отправленный отдельно на `qwen3.5:4b` и на `itmo-local` **непосредственно во время этого повторного аудита** (не в момент исходных замеров), дал побайтово идентичный текст ответа — сохранено в `lab/results/tagcheck-qwen-vs-itmolocal.json` (`identical_text: true`). Это подтверждает эквивалентность только для данного конкретного запроса и текущего состояния сервера Ollama; оно **не доказывает**, что исходный запуск `cold42.json` (сделанный в другое время, с другим состоянием модели в памяти) дал бы идентичный текст или тайминг при теге `itmo-local`; тайминги (`wall_seconds`/`load_seconds`) в принципе зависят от состояния кэша/памяти сервера в момент запроса и разными тегами не переигрывались.
Эксперимент не был полностью переигран на едином теге модели: этот A/B-эксперимент необязателен по актуальному `README.md` практики (обязательны только 5 вопросов агента). Ограничение сопоставимости: один из трёх замеров серии A (seed=42) технически получен на `qwen3.5:4b`, а не на `itmo-local`, как утверждалось ранее; для текста ответа при temp=0.2 это, по данным контрольной проверки, скорее всего не имело значения, но для сравнения таймингов между сериями A и B это ограничение не снято.

## Повторный аудит и проверка готовности к демо (29.09.2026)

Ниже — независимая проверка ранее записанных результатов и один дополнительный вопрос, не входивший в исходные QUESTIONS.md. Сверка целостности прежних данных:
- `ollama list`/`ollama ps` и `curl http://localhost:11434/api/tags` повторно подтвердили наличие локальных весов `itmo-agent`/`itmo-local`/`qwen3.5:4b` (GGUF, Q4_K_M, 4.7B) на этом устройстве — расхождений с REPORT.md нет.
- Для сессий вопросов 1 и 4 (`ses_f286e02daffeJW1WNeVpWM1V2g`, `ses_f2853a66effeTSdnbys95aiavA`) выполнен `opencode export <sessionID>`; компактные извлечения сохранены в `lab/results/session-exports/q1-reasoning-extract.json` и `q4-reasoning-extract.json` (только части `text`/`reasoning` и `sessionID`, без полных путей/токенов сессии). **Подтверждённый факт** (не предположение): в обоих случаях полный текст правильного ответа действительно присутствует дословно в частях `reasoning`, а в финальном сообщении отсутствует часть типа `text` — то есть при `format json` CLI не печатает то, что осталось только в `reasoning`. **Причина не установлена**: почему в этих случаях не появился отдельный `text`-шаг после `reasoning`, не выяснено. Возможные факторы включают поведение самой модели, парсинг ответа `qwen3.5` в Ollama, либо способ, которым OpenCode интерпретирует ответ провайдера `openai-compatible` — ни один из этих уровней не был изолированно протестирован, и причину нельзя приписывать исключительно модели.
- Живая проверка канала OpenCode → Ollama (новый вызов, не из старых логов): `opencode run --dir lab/demo --agent local-guide --model ollama/itmo-agent --format json "Скажи одно слово: тест"` → ответ `text: "тест"`, `reason: stop`, локальный HTTP-эндпойнт `http://localhost:11434/v1` использован через провайдер `ollama` (лог сохранён, не закоммичен как файл — воспроизводимо командой выше).
- Read-only ограничение: конфигурация `demo/opencode.json` задаёт `permission: {"*": "deny", "read": "allow", "glob": "allow", "grep": "allow"}`. Наблюдаемые события: во всех 9 исходных сохранённых сессиях (список — в следующем разделе) модель вызывала только инструменты `read`, `glob`, `grep`; событий `tool_use` с `write`/`edit`/`bash` не зафиксировано ни разу. Отдельно модели дважды прямым текстом предлагалось использовать `write` и `bash` (`opencode run ... --auto "Создай файл ... используй инструмент write"` и `"Выполни команду bash: touch probe2.txt"`); в обоих случаях модель ответила текстом, что таких инструментов у неё нет («Мои доступные функции: read, glob, grep» — `lab/results/probe-write-attempt.jsonl`, `probe-bash-attempt.jsonl`), файлы `test_write_probe.txt`/`probe2.txt` на диске не появились. **Это высказывание модели о себе, а не техническая проверка списка инструментов, переданных ей сервером** (например, через инспекцию tool-schema запроса к Ollama) — событий `tool_use` для `write`/`bash` в логе действительно нет, но сам факт отсутствия попытки вызова не эквивалентен независимо подтверждённому списку доступных инструментов. Механизм отклонения permission (что произошло бы, если бы модель всё же попыталась вызвать запрещённый инструмент) не наблюдался ни разу — ни в исходных сессиях, ни в целевых пробах, это предел проверяемости в рамках выполненных запросов.

Дополнительный вопрос (не из QUESTIONS.md, эталон подготовлен агентом заранее по коду, до запуска модели):

> Приводит ли функция `subscribe()` имя подписчика к нижнему регистру перед сохранением? Подтверди кодом.

Эталон (подготовлен по `lab/demo/service.py:4-8` до запуска модели): нет, функция вызывает только `.strip()` (обрезка пробелов), `.lower()`/`.casefold()` нигде не вызывается — значит `"Ann"` и `"ann"` будут сохранены как два разных элемента множества `subscribers`.

Результат модели (новая сессия, `results/q6-demo-unplanned.jsonl`, sessionID `ses_f13cde5cbffeMBxEWHnwcvG3vM`): после `glob`, `read opencode.json`, `grep subscribe\(`, `read service.py` дан видимый text-ответ — «Не приводит. Код в `service.py`, строка 7 хранит имя с сохранением регистра (только удаляет лишние пробелы через `strip()`): `subscribers.add(name.strip())`» — **совпадает с эталоном**, ответ показан пользователю (`reason: stop` с непустой `text`-частью), в отличие от вопросов 1 и 4.

Наблюдение (не строгое доказательство причины): на новом вопросе того же типа (код+file:line, вопрос ниже) модель показала полный видимый ответ. - Ошибка неполного/нерелевантного поиска (узкий `grep`/`glob`-паттерн вместо чтения найденного файла) не устранена как класс — воспроизвелась в новом виде (`grep` вместо `glob`) даже после правки инструкций.
- LM Studio как альтернатива не тестировалась.

## Сценарий демонстрации (воспроизводимо, все команды из `practices/practice_03/`)

Все команды ниже выполняются последовательно из одной директории `practices/practice_03/` (перейти туда один раз командой `cd practices/practice_03` от корня репозитория; далее — без дополнительных `cd`, только относительные пути в аргументах).

```bash
# 0. Если сервер Ollama не запущен (команда ниже вернёт ошибку подключения),
#    запустить его в отдельном терминале одним из способов:
#      - приложение Ollama.app (запускает фоновый сервис на macOS), или
#      - в терминале: ollama serve
#    и дождаться готовности перед следующим шагом.

# 1. Убедиться, что Ollama запущен и модели на месте
ollama list                                   # должны быть itmo-agent, itmo-local, qwen3.5:4b
curl --fail http://localhost:11434/api/tags   # HTTP 200, JSON со списком моделей

# 2. При необходимости (пере)создать кастомные модели из Modelfile (идемпотентно)
ollama create itmo-local -f lab/Modelfile

# 3. Прогнать учебные тесты демо-сервиса

# 4. Обратиться к локальному read-only агенту OpenCode (модель локальная, без облака)
opencode run --dir lab/demo --agent local-guide --model ollama/itmo-agent --format json \
  "Как запустить тесты? Укажи файл-источник."
```

Наблюдение с проверок этого сценария (не гарантированное поведение при каждом запуске): этот же вопрос (вопрос 1) с одинаковыми инструкциями был задан в трёх разных сессиях в ходе работы над отчётом — два раза получен видимый `text` (`lab/results/retest-after-fix/q1.jsonl`, `lab/results/retest-after-fix/q1-repeat3-scenario-verify.jsonl`, sessionID `ses_f13208e91ffemmaaBuHkms4R3W`), один раз текст был пустым при непустом `reasoning` (`lab/results/retest-after-fix/q1-repeat2-scenario-check.jsonl`). Заранее нельзя предсказать, какой результат будет при конкретном запуске на демонстрации — это описанное в отчёте открытое ограничение, а не гарантированная или исключённая реакция.

Как увидеть вызовы инструментов и проверить ответ (по фактической структуре событий в сохранённых логах):
- Флаг `--format json` печатает построчный JSON, каждая строка — одно событие с полем `type` на верхнем уровне и вложенным объектом `part`.
- Событие вызова инструмента имеет верхнеуровневый `type: "tool_use"`; внутри `part.tool` — имя инструмента (`read`/`glob`/`grep`), `part.state.input` — переданные аргументы, `part.state.output` — результат вызова (например, содержимое прочитанного файла или список найденных путей).
- Видимый ответ модели — отдельное событие с верхнеуровневым `type: "text"`; сам текст находится в `part.text`. Если такого события в потоке нет, значит видимого ответа не было (даже если `reasoning` содержал верный вывод).
- Завершение шага — событие `type: "step_finish"`; причина остановки — в `part.reason` (`"tool-calls"` — модель продолжит вызовы инструментов; `"stop"` — генерация завершена).
- Чтобы посмотреть полную историю сессии, включая внутренний `reasoning` (недоступный в потоке `--format json`), использовать `opencode export <sessionID>` (`sessionID` печатается в каждой строке JSON-потока на верхнем уровне).
- Read-only ограничение конфигурации можно проверить, прямо попросив модель записать файл или выполнить команду, например: `opencode run --dir lab/demo --agent local-guide --model ollama/itmo-agent --format json --auto "Создай файл x.txt"`. В ранее сохранённой проверке (`lab/results/probe-write-attempt.jsonl`) модель ответила текстом, что у неё нет инструмента `write`, и файл не появился на диске — это наблюдение по конкретному прогону, а не гарантия одинаковой реакции при каждом запросе.

Краткое объяснение конфигурации для защиты:
- Модель — `qwen3.5:4b` (Alibaba, GGUF, Q4_K_M, 4.7B, Apache-2.0), загружена и выполняется локально через Ollama (`ollama.com/library/qwen3.5`), без обращения к облачным API.
- `lab/Modelfile` / `lab/Modelfile.agent` создают два кастомных тега (`itmo-local` для прямых API-вызовов с фиксированным system prompt; `itmo-agent` для OpenCode с расширенным контекстом 65536).
- `lab/demo/opencode.json` подключает OpenCode к локальному Ollama через `openai-compatible` провайдер (`baseURL: http://localhost:11434/v1`) и описывает read-only агента `local-guide` (permission `deny *`, кроме `read/glob/grep`), с инструкциями из `lab/demo/repo-system.txt`.
- Ограничения: модель иногда не выводит видимый ответ, хотя знает его (эффект наблюдался и до, и после правки инструкций; причина не установлена и не приписывается только модели); может использовать слишком узкий или нерелевантный `glob`/`grep`-паттерн и не перепроверять находку чтением всего файла; A/B-эксперимент по temperature содержал разнобой тегов модели внутри серии A (описано и частично, но не полностью, проверено контрольным запросом); офлайн-режим не проверялся.
