# Разработка Notify Mini

Все пути ниже указаны относительно `practices/practice_03/`.
Скилл предназначен для рабочего агента, который изменяет учебный сервис.

## Когда применять

Применяй при разработке функций сервиса, исправлении ошибок и изменении связанных тестов. Для запуска экспериментов с локальной моделью и оформления их результатов используй отдельный скилл `practice-03-local-models`.

## Перед изменениями

1. Прочитай `AGENTS.md`, проверь `git status --short --branch`. Рабочая ветка — `practice_04`.
2. Изучи `lab/demo/service.py`, `lab/demo/test_service.py`, `lab/demo/README.md`, `lab/QUESTIONS.md` и Makefile, относящиеся к запуску проверок.
3. Сформулируй контракт изменения: входные данные, результат, ошибки, побочные эффекты и повторный вызов. Различай текущее поведение кода и запланированное.
4. Сохраняй принятые в проекте правила, если пользователь явно не запросил их изменение: стандартная библиотека Python 3.10+, тесты `unittest`, хранение подписчиков в памяти процесса, удаление пробелов по краям имени и чувствительность к регистру.

## Согласованная фича: отписка

Этот раздел описывает требования к будущей реализации, а не утверждает, что функция уже существует. Перед работой проверь код.

Добавить `unsubscribe(name)` для строковых имён:

| Условие | Ожидаемое поведение |
|---|---|
| Имя есть в подписчиках | Удалить его и вернуть `{"unsubscribed": True}` |
| Имени нет или отписка повторена | Вернуть `{"unsubscribed": False}` без исключения |
| По краям имени есть пробелы | Применить `strip()` перед поиском |
| Имя пустое или состоит из пробелов | Выбросить `ValueError("empty name")` |
| Имена отличаются регистром | Считать их разными, как в `subscribe` |

Отписка одного пользователя должна сохранять остальных подписчиков. Существующий контракт `subscribe` должен продолжать выполняться.

## Реализация и проверки

1. Внеси минимальное изменение в `lab/demo/service.py` в стиле существующего кода.
2. Добавь поведенческие тесты в `lab/demo/test_service.py`: успешная отписка, неизвестное имя, повторная отписка, пробелы, пустая строка и строка из пробелов, различие регистра, сохранение остальных подписчиков. Проверяй и результат функции, и состояние множества. Используй существующую очистку состояния в `setUp`.
3. Обнови `lab/demo/README.md`: назначение функции, возвращаемые значения и ошибки.
4. Выполни `make test` из папки практики. При ошибке устрани причину и повтори проверку. Указывай только фактически полученные результаты.

## Согласованность вопросов для модели

После изменения кода перечитай все пять вопросов в `lab/QUESTIONS.md`. В наборе должны оставаться вопрос без ответа в репозитории и вопрос с ложной предпосылкой.

После реализации `unsubscribe` вопрос «Где реализован unsubscribe?» перестанет содержать ложную предпосылку. Замени его, например, на «В какой таблице базы данных функция unsubscribe сохраняет историю отписок? Проверь предпосылку вопроса», предварительно убедившись, что код действительно не содержит такого хранения.

Эталоны и пояснения о правильности ответов не добавляй в инструкции тестируемой модели. Существующие логи и результаты в `REPORT.md` относятся к прежней версии кода: сохраняй их как историю, не переписывай под новую реализацию. Для новой оценки используй отдельный прогон по скиллу `practice-03-local-models`.

## Завершение

- Выполни `git diff --check` и `git status --short`; проверь также содержание новых неотслеживаемых файлов, которые обычный `git diff` не показывает.
- В ответе перечисли изменённые файлы, выполненные проверки и оставшиеся задачи.
- Для демонстрации покажи вызов этого скилла, согласованный контракт, изменение кода и реальный вывод тестов. Само наличие `SKILL.md` не является доказательством его применения или улучшения качества модели.
