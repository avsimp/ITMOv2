# Design

## Context

Мотивация и границы поведения — в `proposal.md`; контракт — в `specs/homework-delivery/spec.md`. Design нужен из-за взаимодействия HTML, PDF-аннотаций, ZIP, manifest и ответа MCP.

Наблюдения по текущему проекту, пути относительно папки практики:

- `homework/server.py:39–46` передаёт `create_pdf` в `render.export_pdf` без собственной логики экспорта.
- `homework/render.py:45–103` получает задачи в порядке ID, встраивает картинки, скачивает все `a[href]`, печатает PDF и пишет sidecar-файлы. Приложения уже находятся в памяти до записи.
- Имена сейчас содержат ID, хеш URL и исходное имя. Замена `href` не меняет подпись. Оригинальные задачи записываются в manifest без замены HTML.
- Проверка существования охватывает PDF, answers, sources и `.files`, но не ZIP.
- Из восьми автономных тестов успешный экспорт не проверяет ни один. Живое демо проверяет PDF и ODS, но не PDF-ссылки.
- Во время планирования прочитаны PDF-аннотации сохранённого `evidence/run-20261007-211312-806726/таблица.pdf`: `get_links()` вернул пустой список для единственной страницы. Наличие `href` в HTML не доказывает работоспособность ссылки в PDF.
- Baseline из explore: `make check` в `homework/` — 8 passed, Ruff успешен. После планирования baseline повторно не запускался.

## Goals / Non-Goals

**Goals:**
- Один план соответствий приложений для имени на диске, ссылки PDF, ZIP и sources, без независимых схем переименования.
- Дополнительный ZIP и поля ответа без изменения сигнатуры MCP и оформления PDF.
- Проверка переносимости настоящего PDF независимо от HTML и текущего каталога экспорта.

**Non-Goals:**
- Общий механизм транзакционной публикации файлов, очередь экспортов или переработка кеша.
- Поддержка других источников, эвристическая классификация ссылок, изменение правил выбора задач.
- Просмотр приложений, конвертация их содержимого или распаковка исходных ZIP.

## Decisions

### 1. Один экспорт и совместимое расширение ответа

Оставить `create_pdf(topic_ids, output_path)` и требование абсолютного `.pdf`. Для `урок.pdf` вычислять пути `урок.zip`, `урок.files`, `урок.answers.txt`, `урок.sources.json` рядом с PDF. ZIP и `.files` появляются только при непустом наборе приложений.

Существующие поля ответа сохраняются. Добавляются:
- `result_file`: абсолютный путь ZIP при наличии приложений, иначе PDF;
- `archive`: абсолютный путь ZIP либо `null`.

`attachments` остаётся списком локальных имён, теперь пронумерованных. Инструкция агента указывает первым `result_file`, продолжая открывать `pdf` для визуальной проверки и выдавать преподавателю ответы отдельно.

Альтернатива — новый MCP-tool или входной путь `.zip` — требует изменения клиентов и не нужна для этого поведения.

### 2. План приложений до изменения HTML

Для каждого пункта разобрать исходный `statement_html`, собрать уникальные точные URL всех `a[href]` в порядке первого появления. Это сохраняет нынешнее определение приложения. Сначала определить число уникальных URL пункта, затем назначить имена: один файл — номер; несколько — номер и индекс с единицы.

Исходное имя получать из последнего компонента пути URL, декодируя percent-encoding; query не является частью имени. Сохранять последовательность суффиксов и регистр (`data.tar.gz` → `2.tar.gz`, `DATA.ODS` → `2.ODS`); без суффикса оставлять только номер. Пустое имя пути трактовать как отсутствие расширения. Эти правила — принятые проектные defaults для неуточнённых краевых случаев.

Повтор точного URL внутри пункта использует одну запись плана и один локальный файл. В разных пунктах тот же URL получает разные номера; кеш банка может избежать повторной загрузки. Разные URL не объединять по имени или байтам: иначе можно потерять отдельное приложение.

План хранит номер пункта, ID задачи, исходный URL, исходное имя, новое имя и относительный путь `<основание>.files/<новое имя>`. Использовать небольшие вспомогательные функции в `render.py`; отдельная подсистема не требуется.

Альтернатива — назначать имя при каждом обходе ссылки — не позволяет заранее различить одиночный файл и набор, а одинаковые имена могут затереть друг друга.

### 3. Отдельный HTML для PDF и неизменные оригиналы

Менять только разобранную копию HTML. Видимый текст ссылки сравнивать с декодированным исходным именем без обрезки и изменения регистра; при точном совпадении заменять текстовым узлом нового имени. Иные подписи и остальной текст условия не менять. Если совпадающее имя обёрнуто в оформляющий тег внутри ссылки, сохранить эту оболочку при замене текста.

Оригинальные объекты `tasks` и их `statement_html`/URL не менять. В manifest оставить текущие поля, включая `attachments` с новыми именами, и добавить `attachment_map` — упорядоченный список записей с полями `task_number`, `task_id`, `source_url`, `original_filename`, `filename`, `relative_path`. Для экспорта без приложений — пустой список. Это аддитивное расширение формата версии 1, позволяющее сопоставить локальный файл с оригиналом без изменения исходных данных.

Альтернатива — заменить имена непосредственно в `tasks` — уничтожает оригинал источника и затрагивает другие потребители банка.

### 4. Настоящие относительные ссылки в PDF

Для печати назначать ссылкам уникальные абсолютные маркеры на зарезервированном домене `homework.invalid`, сопоставленные плану приложений. Они нужны только как надёжно распознаваемые PDF-аннотации, а не как сетевые ресурсы; блокировка запросов страницы сохраняется.

После Chromium-печати нормализовать только маркерные аннотации через PyMuPDF в файловые ссылки с относительным назначением `<основание>.files/<имя>`. Если аннотация для исходной ссылки потеряна, экспорт должен завершиться объяснимой ошибкой, а не сообщить успех. Проверять наличие назначений для всех ссылок, включая повторные; многострочная ссылка может занимать несколько аннотаций. Маркерных и абсолютных локальных адресов в итоговом PDF не оставлять.

PyMuPDF уже используется `verify_live.py` и указан в `requirements-dev.txt`. Перенести его в runtime `requirements.txt` с проверенной зафиксированной версией и убрать дублирование dev-зависимости. Это изменение области установки существующего пакета, а не введение второго PDF-движка для вёрстки. Без приложений PDF-постобработку не выполнять. `pdf_sha256` считать по окончательным байтам после нормализации.

Альтернативы: один относительный HTML `href` уже не дал аннотаций в сохранённом примере; `file://` с абсолютным путём не переносится; собственное редактирование PDF без библиотеки сложнее и хуже проверяется.

### 5. ZIP по явному списку

Использовать `zipfile` стандартной библиотеки. Записать ровно PDF с его basename и приложения с относительными POSIX-путями из плана. Не обходить каталог рекурсивно и не включать sidecar-файлы. Структура рядом с архивом и после распаковки одинакова:

```text
export/
+-- lesson.zip
+-- lesson.pdf
+-- lesson.files/
|   +-- 2.ods
|   +-- 4_1.txt
|   +-- 4_2.txt
+-- lesson.answers.txt
+-- lesson.sources.json

lesson.zip
+-- lesson.pdf
+-- lesson.files/
    +-- 2.ods
    +-- 4_1.txt
    +-- 4_2.txt
```

Имена с кириллицей и пробелами сохранять, содержимое приложений не менять. ZIP формировать после готовности финального PDF и приложений, возвращать успешный ответ только после завершения всех записей.

### 6. Проверка конфликтов до загрузки и записи

Добавить ZIP к существующей проверке всех пяти целевых путей до получения задач и записи результатов; проверять его и для экспорта без приложений. Любой конфликт возвращает `SourceError` без создания новых материалов. Для создаваемых файлов использовать эксклюзивное создание, для каталога приложений — создание с отказом при существовании; преобразовывать конфликт в понятную ошибку. ZIP открывать в режиме создания без перезаписи.

Это сохраняет пользовательское правило и закрывает риск затереть файл, появившийся после предварительной проверки. Общая атомарность всего набора при сбое диска или параллельных экспортах не вводится: возможные частичные новые результаты не считать успешным экспортом.

### 7. Проверки на двух уровнях

Автономные тесты с синтетическим банком проверяют содержимое ZIP, побайтовую неизменность приложений, отсутствие answers/sources, смешанные пункты, коллизии имён, повтор URL, подписи, оригинальный manifest, конфликт каждого пути и ответ API. Существующие восемь тестов сохраняются.

Отдельный автономный интеграционный тест использует установленный Chromium, синтетические задачи и настоящую печать PDF, без сети. Он распаковывает ZIP в другой временный каталог, читает PDF-аннотации PyMuPDF и проверяет относительные назначения и существование соответствующих файлов. Простого сравнения HTML для этой проверки недостаточно. Включить кириллицу/пробелы в имени экспорта, блок 19–21 перед приложением и содержательную подпись.

`verify_live.py` дополнительно проверяет новые поля и архив на реальных MCP-вызовах. `make check` — основная проверка из `homework/`; `make demo` — отдельная живая проверка при доступности источника. Визуальный просмотр PDF проверяет отсутствие изменения вёрстки; ограничения просмотра ссылок конкретным PDF-просмотрщиком фиксируются отдельно от проверки назначений.

## Risks / Trade-offs

- Потеря или неверное назначение аннотаций Chromium → тест настоящего PDF, сверка маркеров и отказ при пропаже ссылки.
- Поддержка открытия локальных файлов отличается между просмотрщиками → использовать стандартные относительные файловые ссылки, проверить извлечённые назначения и открытие в доступном локальном просмотрщике; не подменять результат проверкой HTML.
- Увеличение runtime-окружения за счёт PyMuPDF → использовать уже применяемый проектом пакет и сохранить Chromium единственным движком вёрстки.
- Дублирование приложений на диске и в ZIP → это принятое требование; поток загрузки и лимит 100 задач остаются прежними.
- Ошибка записи после создания части новых файлов → не возвращать успех, сохранять запрет перезаписи и выбирать новое имя для повтора; не добавлять общий механизм rollback в эту фичу.

## Migration Plan

1. Реализовать изменение и обновить зависимости через обычную установку проекта; выполнить `make check`.
2. Обновить описание MCP и инструкцию выдачи, запустить новую MCP-сессию и проверить её через `make demo`; результаты сохранять в новом `output/run-*`, не заменяя evidence.
3. Старые экспорты не мигрировать и не перепаковывать. Новые используют новую нумерацию и дополнительные поля ответа.
4. Для отката вернуть код, документацию и зависимости предыдущей версии. Ранее созданные ZIP/PDF остаются пользовательскими результатами и автоматически не удаляются.
