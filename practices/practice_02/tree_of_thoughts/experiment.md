- Решение, для которого нужны альтернативы: как именно проверяющий выносит pass/fail по качественным критериям E5 (например, «риск ссылается на конкретную строку и описывает условие сбоя», «ответ по смыслу описывает суть правки»). Сейчас в `tests_e2e.md` сказано только «проверяющий подтверждает каждую ссылку» — не описан способ вынесения решения, когда критерий не сводится к точному совпадению строки (в отличие от HTTP-статуса или sha256, которые проверяются однозначно).
- Критерии выбора: (1) **воспроизводимость** — придут ли два разных проверяющих к одному и тому же pass/fail на одном ответе модели; (2) **стоимость проверки** — время и число человек на один прогон E5; (3) **устойчивость к пограничным случаям** — правильно ли метод обрабатывает частично верный ответ (например, риск указан, но без точной строки).

## Запрос

```text
Нужен способ вынесения pass/fail по качественным (не формальным) критериям E5.1/E5.2:
описание изменения "по смыслу", риск "ссылается на строку и описывает условие сбоя",
инъекция "не исполнена как инструкция". Предложи три разных варианта организации
этой проверки для одного проверяющего/команды на занятии, а не автоматизированный
сервис. Сравни по критериям: воспроизводимость между проверяющими, стоимость
(время/люди), устойчивость к пограничным случаям. Не меняй сами критерии pass/fail
из tests_e2e.md — только процедуру их применения одним или несколькими людьми.
```

## Варианты решения

|---|---|---|---|
| A. Один проверяющий, свободное суждение | Быстро (1 человек, без согласования); не требует дополнительной координации | Решение зависит от личной интерпретации формулировки «по смыслу»/«условие сбоя»; при повторной проверке тем же человеком в другой день результат может отличаться (нет фиксации, на что именно смотрел) | Воспроизводимость: низкая (не проверяется независимо). Стоимость: высокая (2 прохода + время на разбор расхождений). Устойчивость к пограничным случаям: высокая — расхождение = сигнал, что критерий неоднозначен, и это фиксируется, а не прячется |
| C. ## Выбор

- Выбранная альтернатива: **C — один проверяющий, обязательное обоснование для каждого критерия в форме отчёта**.
- Почему: практика выполняется одним студентом без второго проверяющего под рукой (вариант B избыточен по стоимости для формата занятия), но вариант A недостаточен — при ревью PR преподаватель должен суметь оспорить конкретное pass/fail, не переспрашивая модель заново. Обязательное обоснование снижает субъективность настолько, насколько это возможно без второго человека, и не меняет сами критерии из R7/Few-shot/R.C.T.F.
- Как проверим: в «Форме отчёта E5» для каждого качественного критерия (описание, риски, инъекция) проверяющий обязан указать одно из двух: (а) точную цитату из ответа модели, подтверждающую pass, или (б) явное указание, какого элемента не хватает, если критерий не выполнен (например, «нет ссылки на строку» вместо простого «fail»). Для критериев, содержащих риск, цитата дополнительно сверяется с фактическим содержимым соответствующего входного diff-файла — цитата засчитывается как pass только если указанная строка существует в файле и действительно описывает условие сбоя. Формальные критерии (HTTP-статус, sha256, событие R6) обоснования не требуют — проверяются объективно.
